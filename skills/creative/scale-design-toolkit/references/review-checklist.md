# Design review checklist

Use the checks that apply to the actual deliverable. Record the tested revision and result; do not mark a check passed from a source description, mockup or package installation.

## Outcome and content

- [ ] The main action and its result match the project brief.
- [ ] A new user can identify what the page is for and what to do next.
- [ ] Navigation, statistics, cards and controls serve this screen's task.
- [ ] Labels, examples, prices and proof are real or explicitly marked as illustrative.
- [ ] The hierarchy survives long names, missing images, large values and empty content where relevant.

## Visual coherence

- [ ] Typography, color roles, spacing, control shapes and icons follow one direction.
- [ ] References inform named decisions; the result suits this project's brand.
- [ ] Text contrast, legibility and visual focus have been checked in the actual output.
- [ ] Imagery explains the product or idea and has a recorded source and permitted use.
- [ ] Decorative effects leave the main content and action clear.

## Interaction and states

- [ ] Every visible control has the expected effect.
- [ ] Empty, loading, error, success and permission states are covered where the interaction needs them.
- [ ] Feedback appears where the action happened, with sufficient reading time.
- [ ] Keyboard navigation, focus visibility, dismissal and return of focus work where relevant.
- [ ] Phone layout and touch behavior were checked separately from desktop.
- [ ] Existing data, links, accounts and unrelated behavior remain correct.

## Motion and media

- [ ] Motion explains a change or responds to an action.
- [ ] Timing was reviewed in playback, including opening, exit and loop seam.
- [ ] Reduced-motion and static/poster states communicate the result.
- [ ] Animation does not obscure controls, distort text or cause unwanted layout movement.
- [ ] A scripted illustration is identified as a demo, not proof of a real app operation.
- [ ] Relevant runtime weight and performance were checked on the actual target.

## Reuse and delivery

- [ ] Resource versions, code licenses, asset licenses and attribution are recorded.
- [ ] Existing components were considered before adding a dependency.
- [ ] The project has the accepted brief, tokens, component states and real screenshot or clip.
- [ ] Validation results identify what passed, what was not checked and what remains open.
- [ ] Resource status is accurate: reviewed, trial candidate, tested or adopted.
- [ ] The deliverable is accepted before the task is marked complete.
