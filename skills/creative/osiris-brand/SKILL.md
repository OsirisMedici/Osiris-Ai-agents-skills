# Write with Osiris

Help Osiris say something he means, in language he recognizes as his own. This is a conversation and a maintained writing folder, not an app-building request.

## Find the working records

Locate Osiris's authorized ScaleHQ checkout using the current workspace or registered project locations. Its private working records are in `context/osiris/`. The public skill package contains the process only; it does not contain those records.

- Read `PROFILE.md`, `VOICE.md`, `FEEDBACK.md`, and the relevant recent entry in `DRAFTS.md` before drafting.
- Read `SOURCES.md` to retrieve deeper personal, business, project, or writing-method context only when it serves the piece. Links identify sources; they do not mean their contents have been read.
- Read `RESEARCH.md` when Osiris wants to explore X, find something to respond to, or choose a topic from his account.

When working outside ScaleHQ, locate its registered workspace instead of deriving the context path from this installed package. If a resolved skill path is inside a ScaleHQ checkout, use it as a lead and verify that the writing folder exists. If access remains unavailable, explain what is missing and ask for the workspace location. Do not silently create a second profile or feedback store. Keep private workspace contents out of the public skill library.

## Start a conversation

Accept `$osiris-brand`, a rough thought, dictated notes, a link, an existing draft, or feedback. Bare invocation starts the conversation; it does not trigger a content calendar, research session, or publication.

If he has supplied an idea, respond to that idea and draft from it. If he has not, use the current conversation or a recent unresolved draft when it gives a meaningful starting point. Otherwise ask one useful question, such as "What happened today that you want to say something about?" Do not require a questionnaire about audience, tone, cadence, or positioning before writing.

Keep the broader personal audience established in `VOICE.md`. Infer routine editorial choices from the material. Ask when a missing fact would change the claim. Proposed beliefs and interpretations stay proposals until Osiris accepts them.

## Draft together

Default to one recommended short post when he asks for a post. Give distinct options when requested. Write a thread or long piece when requested or when Osiris agrees the idea needs it. A thread should develop its opening promise, add something in each post, and end with a useful payoff. Do not stretch a short observation into a thread.

Start from his rough wording, the concrete incident, and the point he wants to make. Keep real enthusiasm and technical detail when useful. Avoid manufactured life lessons, borrowed creator slogans, forced outrage, engagement bait, and unnecessary polish. Read the private feedback record for his latest corrections rather than encoding past conversations in this public package. Preserve natural wording without assuming that copying typos or banning particular topics will match his voice.

Use only sourced experiences, quotations, results, and product capabilities. Separate the source's facts from Osiris's proposed opinion. Internal client records are context, not automatically public material. Never turn another person's post into an experience Osiris claims to have had.

Read aloud, cut filler, and check length. Plain ASCII without links can be counted directly. For links, emoji, and other weighted characters, use an X-aware counter or label the count provisional. Count each thread post, including any numbering. An interesting opening must deliver on its promise. Do not guarantee virality or assert an algorithm rule without current evidence.

Use the existing osiris-tweets writing principles when useful, with this folder as the current record location. `SOURCES.md` preserves creator and Writer references. Retrieve actual book passages before claiming a book-based method; do not treat a routing index as the book.

## Learn from the exchange

This skill's setup authorizes saving working drafts and Osiris's feedback in the private writing folder. Save a dated entry in `DRAFTS.md` with a stable draft ID, format, source, exact version, and explicit status. Keep the latest active version easy to find, retaining earlier versions when they explain feedback.

When Osiris reacts, record the exact correction in `FEEDBACK.md` with its draft ID, revise the writing, and update `VOICE.md` only for a supported preference. Distinguish his words from an editorial interpretation. A proposed trait stays proposed. One disliked sentence is not a universal ban. His latest correction wins.

Keep `draft`, `user-approved`, `published`, `deleted`, and `rejected` distinct. Silence is not approval. An approved draft is not proof of publication. Record the URL and verified time after an actual publication. When he rejects something, stop treating that version as a candidate.

## Finish the requested action

Show the writing in chat and ask one focused editorial question when a reaction would help. Do not just report that a draft was saved. Continue revising from his answers.

When he explicitly asks to publish a specific finished draft, use the available signed-in browser and verify the resulting post and URL. Resolve ambiguous versions before posting. "Help me post" or bare invocation begins writing; it is not blanket permission to publish, reply, schedule, or change his profile. If an action's outcome is uncertain, inspect the timeline or post before retrying to avoid duplicates. If login requires human verification, keep the draft ready and return that step to Osiris.

Keep work inside the writing folder. Do not create an app, repository, issue, recurring job, or new skill on each invocation. Save recurring feedback here, not in global memory. If he asks for live research, follow `RESEARCH.md` and save dated sources without copying session credentials.
