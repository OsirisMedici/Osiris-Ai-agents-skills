# GHL Visual Newsletter by Scale

Create a polished, reusable email in the client's existing GHL account. Assess native capabilities first; introduce custom HTML or another subscription only when a demonstrated requirement makes it necessary. Treat the selected design and the current brief as constraints, not permission to reuse another brand's assets.

## Establish the working version

- Read the authorized client workspace for the exact sub-account, approved template, assets, restrictions and latest feedback. Confirm the location in the live UI before any write; similarly named accounts can be different locations.
- Resolve the intended reader, the useful idea and the desired next step from existing context. Ask only for a material missing decision.
- For a reference email, inspect the rendered design and available HTML. Plain text cannot establish layout fidelity. Note image sequence, width, typography, spacing, columns, buttons, footer and mobile stacking.
- Preserve the liked version. Duplicate it within the correct account before rewriting or changing projects; use a clear edition/version and draft status in its name.
- Client exports, account IDs, approvals and private links belong in the private task workspace, not this public skill package.

## Build in GHL

Prefer native Design Editor text, image and button blocks when they retain the selected layout and allow the team to make routine updates. A Mailchimp browser-URL import into the Design Editor worked in the source task; inspect the current account's import options and resulting editability before relying on it elsewhere.

Use custom HTML only when the native conversion cannot retain a required layout or behavior. Explain who will maintain the code and what becomes harder to edit. A preview HTML export is a recovery artifact, not a promise of native round-trip editability.

Use connected tools when they support the required account and action; otherwise use the host's supported in-app browser. Follow its browser and mutation rules. Read [editor-notes.md](references/editor-notes.md) when editing or validating the template; it records fragile GHL interactions and saved-state checks.

Replace the original brand's copy, logos, imagery, destinations, social links, contact information and subscriber/tracking links. Recreating layout does not grant rights to the original content. Public website availability does not override a client's usage restriction. In before/after or concept/completed pairs, label each image accurately and keep the intended order when stacked.

## Write the whole letter

Scale's requested direction for this workflow is a relaxed, useful note that can support later conversations. Use one clear idea, concrete project evidence and a small takeaway the reader can use without booking a meeting. Do not turn every photograph into a sales pitch or impose a fixed section count on a different brief.

Rewrite the subject, preheader, headline, opening, section text, button labels, closing and footer as one piece. A practical starting structure is a recognisable reader situation, an illustrated example, a useful question or exercise, then a quiet invitation to reply or explore further. Preserve the chosen client's voice rather than inventing a founder quotation or resident story.

Separate supplied project facts from editorial interpretation. Omit conflicting measurements and unsupported claims until resolved. Do not imply proven lead, meeting or revenue outcomes from a design demonstration.

For work in the Writer project, retrieve its local writing contract and canonical Nicolas Cole PDF before substantive copy work. Relevant method locators: specificity pp. 59–60; headline clarity pp. 141–142; main points pp. 173–174; concise conclusions p. 195; natural language pp. 202–203; reader-first self-reference pp. 206–207. This skill's newsletter structure is an editorial adaptation, not Cole's prescribed email formula. The PDF is not bundled; if a book-only workspace lacks it, identify that gap instead of inventing attribution. GHL facts and client evidence remain separate from writing method.

## Save, review and repeat

Save and reload the actual GHL version. Read back the entire copy and subject/preheader; inspect generated preview HTML when available. Check images, destinations, inherited styles, old-brand remnants and desktop/mobile layout. Distinguish browser preview checks from actual inbox-client tests.

Keep a native master and create a copy per edition. Scale's writer supplies the idea, copy, subject/preheader, image order and links; the GHL editor replaces the native fields; the designated reviewer approves that edition. These roles may be handled by one person. Record the template link, source assets, restrictions, review status and verification in the private task handoff. Export saved HTML if requested or needed for the authorized handoff.

Template creation or revision does not authorize a test send, campaign launch, workflow activation, audience enrollment, sender/domain changes or paid usage. If delivery is separately requested, first resolve the authorized audience, sender/reply handling, unsubscribe/suppression behavior and test recipients. Do not interpret a broad-list aspiration as permission to send the saved draft to every contact.

Verify current account features and official GHL documentation when answering plan, builder or delivery questions. Distinguish already available features, usage-based email charges and a new subscription; do not invent entitlements or prices. End with the saved result, how to review/reuse it, what was verified and any material remaining limitation.
